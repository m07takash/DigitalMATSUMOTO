# ナレッジグラフの書き方ガイド

DigitalMATSUMOTO のグラフRAG（`RETRIEVER: "Graph"`）で使うナレッジグラフを、**手で設計して書く**ためのガイドです。例はすべて同梱サンプルのエージェント **駒木乃英人（`agent_10Sample.json` / `Sample01_Relations`）** を使います。

グラフRAGの設定項目（`rags.json` / KNOWLEDGE・BOOK の検索ポリシー / 可視化）は [README の「グラフRAG（graph型）」](../README.md#グラフraggraph型) を参照してください。このガイドは「どういうグラフを書けば、欲しい知識がちゃんと引けるか」に絞っています。

---

## 1. 全体像：グラフはどこから作られるか

グラフは `user/common/rag/graph/<フォルダ>/graph.json` に保存される、**エンティティ（ノード）と述語付きの辺だけの構造**です。本文は持ちません（本文は Vector RAG 側に置きます）。作り方は3通りあります。

| 経路 | 入力 | LLM | 向いている場面 |
|---|---|---|---|
| **手書きのグラフ列**（本ガイドの主題） | Notion の1行に JSON で三つ組を書く | 使わない | 事実を正確に・安く・自分の設計どおりに入れたい |
| CSV の列マッピング（Lane A） | 1行＝1エンティティの台帳 CSV ＋ `mapping.json` | 使わない | 人物名簿のように、列がそのまま関係になる台帳がある |
| テキストからの LLM 抽出（Lane B） | 自由文 | 使う | 台帳も手書きの余裕もなく、文章しかない |

Notion から取り込む場合は、**1行ごとに「グラフ列が正しく書けていれば手書きを採用、空・壊れていればテキスト列を LLM で抽出」**します。手書きの行は `lane=STRUCTURED`、LLM 抽出の行は `lane=TEXT` として記録され、同じ属性が衝突したときは**手書き（STRUCTURED）が必ず勝ちます**。まず LLM に任せて、大事な行から手書きに置き換えていく使い方ができます。

`rags.json` の例（Notion の「テキスト」列と「ナレッジグラフ」列を持つ DB）:

```json
"Sample01_Relations_Notion": {
    "active": "Y",
    "input": "notion",
    "data_type": "graph",
    "data_name": "NotionDB",
    "bucket": "Sample01_Relations_Notion",
    "file_path": "user/common/rag/graph/sample01_relations_notion/",
    "extractor_agent": "agent_56GraphExtract.json",
    "item_dict": {
        "create_date": {"タイムスタンプ": "date"},
        "graph_json":  {"ナレッジグラフ": "rich_text"},
        "key_text":    [{"テキスト": "rich_text"}],
        "value_text":  {"テキスト": "rich_text"},
        "category":    {"対象": "select"}
    },
    "chk_dict": {"確定Chk": true, "GraphChk": false},
    "date_dict": {},
    "category_dict": {},
    "fin_flg": {"GraphChk": true}
}
```

- `graph_json` … 手書きのグラフ列。ここが読めた行は LLM を呼びません
- `value_text` … グラフ列が空・無効な行だけ、この列が LLM 抽出に回ります。**グラフ列を `value_text` にしないでください**（JSON を LLM に読ませ直すことになります）
- `create_date` … 辺や属性の「いつ時点の情報か（`as_of`）」になります。同じ属性が複数の行から来たとき、新しい方が勝ちます。キーを書かなければ取込日で補完されます
- `category` … その行から作られた辺の `domains` になります

## 2. グラフ列の書式

1行（1つの事実）に対して、次の JSON を1つ書きます。

```json
{
  "triples": [
    {"subject": "主語", "subject_type": "型", "relation": "述語", "object": "目的語", "object_type": "型", "props": {"キー": "値"}}
  ],
  "node_props": [
    {"entity": "対象ノード", "key": "属性名", "value": "値"}
  ]
}
```

| 項目 | 意味 |
|---|---|
| `triples` | 辺（主語 → 述語 → 目的語）。主語・目的語は存在しなければノードとして作られます |
| `subject_type` / `object_type` | ノードの型（`人物` / `組織` / `場所` など）。**最初に付いた型が残ります**。検索のきっかけには使われません（→ 4章） |
| `props` | 辺に付く属性（期間・役割・評価など） |
| `node_props` | ノードに付く属性（生年月日・身長・肩書きなど） |

**採用される条件**（満たさない行は LLM 抽出に回ります）:

- JSON として読める（前後の ` ```json ` フェンスは付いていても可）
- `triples` か `node_props` に、使える要素が1件以上ある
- triple は `subject` / `relation` / `object` の3つとも空でない（空のものはその triple だけ捨てられます）
- node_prop は `entity` と `key` が空でない

> **Notion に貼るときの注意**：値の中の半角スペースは、貼り付けの途中で折り返されて改行に化けることがあります。改行が入ると JSON が壊れて、その行は LLM 抽出に回ってしまいます。`"バー Cielo"` は `"バー Cielo"` のように ` ` で書くと安全です（読み込み時に普通のスペースに戻ります）。

## 3. 何をノードにして、何を属性にするか

| ノードにする | 属性（`props` / `node_props`）にする |
|---|---|
| 他のものとも関係を持ちうるもの、質問の主題になりうるもの | 数値・日付・肩書き・短い説明 |
| 人物・組織・場所・作品・出来事・テーマ | 身長、生年月日、役割、時期、評価 |

**例**：Sample02_Experience の「継父との出会い」（1994/11/3）

> 母が再婚し、姓が駒木乃になった。相手の駒木乃真吾は個人でバーをやっている人で、初対面のとき握手ではなく肩を叩いてきた。

```json
{
  "triples": [
    {"subject": "駒木乃佳代", "subject_type": "人物", "relation": "再婚する", "object": "駒木乃真吾", "object_type": "人物", "props": {"時期": "1994年11月"}},
    {"subject": "駒木乃真吾", "subject_type": "人物", "relation": "経営する", "object": "バー Cielo", "object_type": "組織"},
    {"subject": "駒木乃英人", "subject_type": "人物", "relation": "継子である", "object": "駒木乃真吾", "object_type": "人物"}
  ],
  "node_props": [
    {"entity": "駒木乃英人", "key": "姓の変遷", "value": "佐野 → 駒木乃（1994年、母の再婚による）"}
  ]
}
```

- 「バー Cielo」は、ほかの行（常連客、出来事）とも繋がるのでノードにします
- 「1994年11月」はそれ自体に聞かれることが無いので、辺の `props` にします
- 姓が変わった経緯は、ノードにしても繋がる先が無いので `node_props` にします

**避けたい例**：`{"subject": "駒木乃英人", "relation": "身長", "object": "176cm"}`。「176cm」という、どこにも繋がらない葉ノードが増えるだけです。`node_props` で `{"entity": "駒木乃英人", "key": "身長", "value": "176cm"}` と書きます。

## 4. 検索の仕組みから逆算して設計する

グラフRAGの検索は、次の3つの性質を持っています。ここを押さえると、書くべき形がほぼ決まります。

### 4.1 入口は「ノード名（と別名）」の部分一致だけ

質問文の中に**ノード名か別名がそのまま含まれている**ノードが、検索の起点（シード）になります。`subject_type` / `object_type` は起点選びに使われません。

```text
❌ 「東京」「ブエノスアイレス」に object_type: "場所" を付けただけ
   → 「駒木乃さんが住んだことのある場所は？」で「場所」というノードが無いので、どこからも辿れない

✅ 「東京」「ブエノスアイレス」を「居住地」ノードに繋ぐ
   → 質問に含まれる「居住地」「住んだ」… は別名で拾う（5章）
```

**共通の因子（テーマ、媒体、ジャンルなど）は、型ではなく実際のノードにします。**

### 4.2 辿れるのは2ホップまで、1ノードから辿る辺には上限がある

エージェントの KNOWLEDGE / BOOK の検索ポリシーで決まります。

| キー | 意味 | 影響 |
|---|---|---|
| `HOPS` | 起点から何ホップ先まで辿るか | 2 なら「起点 → 隣 → その隣」まで |
| `FANOUT_LIMIT` | 1つのノードから辿る辺の上限 | 超えた分は捨てられる |
| `EDGE_LIMIT` | 1回の検索で集める辺の総数の上限 | 超えた時点で打ち切り |

1人の主人公に100本の辺をぶら下げると、`FANOUT_LIMIT: 40` なら60本は毎回捨てられます。どれが残るかは辺の重みと日付で決まり、同じ日付に取り込んだ辺ばかりだと**実質、取り込み順の運任せ**です。

### 4.3 「領域 → サブカテゴリ → 具体物」の3段にする

主人公から具体物へ直接辺を張るのをやめ、間に共通因子を挟みます。

```text
駒木乃英人 ─[関心を持つ]→ 取材テーマ ←[属する]─ 移民・難民 ←[分類される]─ ザアタリ難民キャンプ {駒木乃の関わり: 現地取材}
                                     ←[属する]─ 労働       ←[分類される]─ 名前のない働き手たち {駒木乃の関わり: 記事}
```

- **起点が具体物**（「ザアタリ難民キャンプ」）：1ホップで「移民・難民」、2ホップで同じテーマの取材先が並びます
- **起点がサブカテゴリ**（「移民・難民の取材先は？」）：1ホップで取材先がすべて出ます
- **起点が主人公**（「駒木乃さんの取材テーマは？」）：1ホップで「取材テーマ」、2ホップでテーマの一覧が出ます。細部ではなく**目次**が返るので、辺の上限にも引っかかりません

段は3つまでにします。`HOPS: 2` だと、具体物から兄弟の具体物までがちょうど届く深さで、4段にすると届かなくなります。

グラフ列に書くと、たとえば1行はこうなります。

```json
{
  "triples": [
    {"subject": "ザアタリ難民キャンプ", "subject_type": "場所", "relation": "分類される", "object": "移民・難民", "object_type": "カテゴリ", "props": {"駒木乃の関わり": "現地取材"}},
    {"subject": "移民・難民", "subject_type": "カテゴリ", "relation": "属する", "object": "取材テーマ", "object_type": "領域"},
    {"subject": "駒木乃英人", "subject_type": "人物", "relation": "関心を持つ", "object": "取材テーマ", "object_type": "領域"}
  ]
}
```

2本目・3本目の「構造の辺」は、同じ領域に属する行すべてに重複して書いて構いません。同じ辺はまとめて1本になり、どの行から来たかだけが追記されます。むしろ各行に書いておくと、ある行を取り込み対象から外しても構造が崩れません。

### 4.4 領域をまたぐ「本物の繋がり」が深さになる

階層だけだと木になるだけです。グラフらしい深さは、別の領域どうしを結ぶ事実から生まれます。

**例**：Sample03_Impressions「祖父のタンゴシューズ」と Sample02_Experience「祖父にオチョを教わる」

```json
{
  "triples": [
    {"subject": "エドゥアルド・アヤラ", "subject_type": "人物", "relation": "教える", "object": "オチョ", "object_type": "技能", "props": {"時期": "1990年", "場所": "畳の上"}},
    {"subject": "駒木乃英人", "subject_type": "人物", "relation": "習う", "object": "オチョ", "object_type": "技能", "props": {"年齢": "4歳"}},
    {"subject": "オチョ", "subject_type": "技能", "relation": "分類される", "object": "タンゴのステップ", "object_type": "カテゴリ"}
  ],
  "node_props": [
    {"entity": "駒木乃英人", "key": "ペンネームの由来", "value": "祖父に教わった8の字のステップ「オチョ」"}
  ]
}
```

「家族（祖父）」と「仕事（ペンネーム Eight）」が「オチョ」で繋がるので、「ペンネームの由来は？」から祖父の話へ、「祖父のことを教えて」から仕事の話へ、2ホップで届くようになります。

一般常識の事実（「ザアタリ難民キャンプはヨルダンにある」など）を足すのも有効です。ただし**確実に正しいものだけ**にし、人物本人についての事実は元の資料にあることだけを書きます。

## 5. 名前・述語・属性キーをそろえる

### ノード名は「ユーザーが入力する言葉」にする

起点は部分一致で選ばれるので、「嗜好カテゴリ：映像作品」のような管理用の名前は起点になりません。「取材テーマ」「媒体」「家族」のように、質問にそのまま出てくる言葉を選びます。

表記ゆれ（「エイト」「Eight」「英人」）は、別ノードを作らずに `dictionary.json` の `aliases` で1つのノードにまとめます（6章）。

> **短すぎる別名は誤ヒットします。** 部分一致なので、1〜2文字の別名は関係のない質問にも当たります。サンプルの `"母": "駒木乃佳代"` は「母国」「分母」にも当たり、`"自分": "駒木乃英人"` は「自分で調べたい」のような質問でも起点になります。実運用では「駒木乃の母」のような長めの別名にするのがおすすめです。

### 述語は少数に固定する

| 述語 | 使いどころ |
|---|---|
| `分類される` | 具体物 → サブカテゴリ（〜の一種） |
| `属する` | サブカテゴリ → 領域（〜の一部） |
| `関心を持つ` | 主人公 → 領域 |
| 具体的な動詞 | `取材する` `寄稿する` `教える` `経営する` など、事実そのもの |

- 「関連」のような曖昧な述語は避けます。何が繋がっているのか LLM に伝わりません
- 同じ意味の述語を増やさないようにします（`好む` / `好き` / `選好する` / `支持する` が乱立すると、同じ種類の関係として扱えません）

### 評価や強弱は、述語ではなく props の値で表す

```json
{"subject": "季刊SOIL", "relation": "分類される", "object": "寄稿先", "props": {"駒木乃の評価": "最も書きやすい"}}
```

`最も好む` `特に好む` `好む` のように述語を分けるより、キーを1つ（`駒木乃の評価`）に決めて値で差を付ける方が、あとから横断して読めます。

### 自己ループに注意する

主語と目的語が別名によって同じノードになる辺は、**取り込み時に捨てられます**。

```text
❌ {"subject": "Eight", "relation": "呼ばれる", "object": "駒木乃英人"}
   → "Eight" は駒木乃英人の別名なので、自分から自分への辺になり捨てられる
✅ 呼び名は dictionary.json の aliases に書くか、node_props にする
   {"entity": "駒木乃英人", "key": "ペンネーム", "value": "Eight"}
```

## 6. dictionary.json（別名・シード・属性の説明）

グラフフォルダ（`graph.json` と同じ場所）に置く設定ファイルです。取り込み時と検索時の両方で読まれます。サンプルは `user/common/rag/graph/Sample01_Relations/dictionary.json` です。

```json
{
    "aliases": {
        "エイト": "駒木乃英人",
        "Eight": "駒木乃英人",
        "英人": "駒木乃英人",
        "祖父アヤラ": "エドゥアルド・アヤラ",
        "継父": "駒木乃真吾",
        "シエロ": "バー Cielo",
        "ATLAS": "ATLAS日本版"
    },
    "seeds": [
        {"name": "駒木乃英人", "type": "人物", "aliases": ["エイト", "Eight", "英人"], "domains": ["家族", "仕事", "ルーツ"]}
    ],
    "prop_schema": {
        "役割": {"description": "そのエンティティの立場・肩書き"}
    }
}
```

| キー | 取り込み時 | 検索時 |
|---|---|---|
| `aliases` | グラフ列に書かれた名前を正式名に寄せる（「継父」と書いても「駒木乃真吾」ノードになる） | 質問に別名が含まれていれば、正式名のノードを起点にする |
| `seeds` | グラフがまだ空のとき、無条件にノードとして作る（型・別名・ドメイン付き） | ― |
| `prop_schema` | 属性キーの意味の説明（人間とエージェント向けのメモ） | ― |

Delete Graph DB で消えるのは `graph.json` だけで、`dictionary.json` は残ります。

## 7. 取り込みと作り直し

### Notion から取り込む

1. `rags.json` に 1章のようなエントリを書く
2. Notion の対象行に `確定Chk` を付ける（`chk_dict` の条件に合う行だけが取り込まれます）
3. WebUI の **Update RAG Data** を押す
4. 取り込み終わった行には `fin_flg` の指定どおり `GraphChk` が付き、次回からは対象外になります

### グラフ列を直したのに反映されない

**一度取り込んだページは、グラフ列を書き換えてもスキップされます。** そのページ ID がすでにグラフの辺に記録されているためです。作り直すときは次の手順で行います。

1. WebUI の **Delete Graph DB** で対象グラフの `graph.json` を消す
2. Notion で対象行の `GraphChk` を**すべて外す**
3. **Update RAG Data** を押す

### Excel での編集は「試す」用

Knowledge Explorer のグラフ画面から、ノードと辺を Excel でダウンロードして編集し、アップロードで反映できます。共通因子を足してみて検索が良くなるかを試すのに便利です。ただし、上の手順で作り直すと **Excel での編集は消えます**。効果があった変更は、Notion のグラフ列（正本）に書き戻してください。

### CSV（Lane A）から作る

台帳 CSV と `mapping.json` がある場合は、コマンド1つで毎回まるごと作り直せます（LLM 不要）。

```bash
python3 DigiM_GraphBuilder.py user/common/rag/graph/Sample01_Relations
```

### Notion にグラフ列をまとめて貼るとき

- Notion の表を **ID の昇順**に並べてから貼ります。元の CSV の行順と Notion の並びがずれていると、グラフが別の行に入ってしまいます
- 貼ったあと、何行か開いて「テキスト」と「ナレッジグラフ」の内容が合っているかを確かめてください

## 8. よくある失敗

| 症状 | 原因 | 対処 |
|---|---|---|
| その行だけ LLM 抽出になっている | 値の半角スペースが改行に化けて JSON が壊れた | スペースを ` ` で書く（2章） |
| 別の行の事実がグラフに入っている | グラフ列を行の位置で貼り付けた | ID で突き合わせて貼り直す（7章） |
| 「媒体」「取材テーマ」で聞いても何も返らない | 型（`object_type`）だけで分類していて、その名前のノードが無い | 共通因子を実ノードにする（4.1） |
| 主人公について聞くと関係の薄い辺ばかり返る | 主人公に辺が集中し、上限で切られている | 3段の階層にしてハブを割る（4.3） |
| グラフ列を直したのに変わらない | 取り込み済みのページはスキップされる | `graph.json` を消し、`GraphChk` を外して取り込み直す（7章） |
| 質問にドメイン名を入れると、かえって順位が下がる | 検索ポリシーの `DOMAIN_BONUS` が 1 未満（掛け算なので減点になる） | 1 以上にする（サンプルは `1.3`） |
| 属性の「いつ時点か」が全部同じ日付 | `create_date` を指定していない（取り込み日で補完） | Notion にタイムスタンプ列を作り、`item_dict.create_date` に指定する |
| 辺が作られない | 主語と目的語が別名で同じノードになる（自己ループ） | 呼び名は `aliases` か `node_props` にする（5章） |

## 9. 書いたグラフを確かめる

### 形を見る

Knowledge Explorer のグラフ画面で、ノード数・辺数・次数の多いノードを確認できます。次の状態になっていれば、検索で引きやすい形になっています。

- 次数の多いノードが、主人公ではなく領域やサブカテゴリになっている
- 1つのノードの辺の数が、検索ポリシーの `FANOUT_LIMIT` を大きく超えていない
- どこにも繋がっていない孤立ノードが無い

### 実際に検索してみる

エージェントと同じ検索ポリシーで、質問からどのノードが起点になり、どの辺が取れるかを確認できます（LLM は呼びません）。

```python
import DigiM_Graph as dmg

policy = {"HOPS": 2, "EDGE_LIMIT": 30, "FANOUT_LIMIT": 5, "DOMAIN_BONUS": 1.3}  # agent_10Sample と同じ
r = dmg.search_graph("移民・難民の取材で関わった場所は？",
                     "user/common/rag/graph/Sample01_Relations/", policy)
G, N = r["graph"], r["graph"]["nodes"]
print("起点:", [N[s]["name"] for s in r["seeds"]])
for ei, hop, kind in r["selected"]:
    e = G["edges"][ei]
    print(hop, kind, N[e["source"]]["name"], f"-[{e['relation']}]->", N[e["target"]]["name"])
```

- **起点が空** → 質問の言葉がノード名にも別名にも無い（4.1 / 6章）
- **欲しいノードが出ない** → 起点から3ホップ以上離れているか、途中のハブで切られている（4.2 / 4.3）
- **関係の薄い辺ばかり** → 起点がハブになっている（4.3）

グラフ列を書き換えるたびにこの確認を回すと、「書いたのに引けない」を早い段階で潰せます。
